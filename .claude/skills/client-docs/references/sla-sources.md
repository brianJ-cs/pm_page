# 寫 SLA／維運文件的外部來源

2026-09 查過一輪，以下是實際用得上的部分。審查方多半照第一份對表。

## 1. 資訊服務供應商服務水準協議參考範本（最重要）

TWSA，對應數位發展部《政府資訊服務採購作業指引》之常用 SLA 參考項目。

`https://www.twsa.org.tw/F01/doc/資訊服務供應商服務水準協議參考範本.docx`

> ⚠️ 是 .docx，WebFetch 讀不出來（回傳壓縮後的二進位）。
> 要解就先存檔再用 PowerShell 的 `System.IO.Compression` 取出 `word/document.xml`，
> 把標籤剝掉。做過一次，可行。

**它的骨架**（自己的文件照這個排）：

- **問題嚴重程度分級**——只有三級，各附範例：
  - 層級一 緊急的 (Level 1, Critical)：系統嚴重中斷、影響大量客戶、直接影響收益、
    伺服器停機、資料庫無法連線
  - 層級二 主要的 (Level 2, Major)：次要功能異常，但不影響主要交易
  - 層級三 次要的 (Level 3, Minor)：不影響功能的錯誤訊息或一般諮詢
- **必訂指標**：
  - 系統可用性——`(全月分鐘數 − 當月服務中斷分鐘數) / 全月分鐘數 × 100%`
  - 客服支援時段
  - 服務中斷補償
  - 問題回應時間
  - 復原點目標（RPO）
- **服務水準協議之例外說明**

**它的範例數字**（可以直接引用）：
- 回應時間：`Level-1 → 3 小時內；Level-2 → 12 小時內；Level-3 → 24 小時內`
- 服務時段：`週一至週五（工作日）OO 時至 OO 時（8 小時），若因國定假日異動則以公告為準`
- 補償：中斷滿 N 小時 →（1）延長保固時數 N 倍（2）月租費每小時扣 OO 元（3）其他損害賠償
- RPO：`每天凌晨 1~3 點備份，最多能回復到前一天以前的資料`

## 2. 需求寫 P1–P4 時怎麼對過去

官方範本是三級，標案需求常寫 P1–P4（ITIL 的寫法）。對應：

`P1 = Level 1 緊急`、`P2 = Level 2 主要`、`P3 = Level 3 次要`、
`P4` 另立為諮詢／文字／外觀調整。

ITIL 的另外兩個慣例值得抄：
- 等級由**影響範圍（Impact）× 急迫程度（Urgency）**判定
- **P1/P2 連續計時（7×24），P3/P4 只計工作時段、非工作時間暫停**
  （人力不足時可以四級全部只計工作時段，但要寫明）

來源：https://blog.invgate.com/itil-priority-matrix

## 3. 回應 vs 修復（最重要的一條實務慣例）

> 「絕大多數維運合約只承諾**回應時間**，不承諾**修復時間**。」

來源：https://www.kmau.com.tw/articles/it-maintenance-sla-guide.html

修復要寫就寫成**目標值**並標示清楚。軟體問題的修復時間取決於根因，
在不知道根因之前無法承諾——這句話本身就可以寫進文件裡當理由。

同一篇的可用率換算（寫進文件很有用）：

| 可用率 | 每月容許中斷 | 每年容許中斷 |
|---|---|---|
| 99% | 約 7.2 小時 | 約 3.65 天 |
| 99.5% | 約 3.6 小時 | 約 1.83 天 |
| 99.9% | 約 43 分鐘 | 約 8.8 小時 |
| 99.95% | 約 22 分鐘 | 約 4.4 小時 |

罰則三層設計：① 根因報告與改善計畫 ② 服務抵減（月費 5%–20%）③ 連續未達標得終止。

## 4. 常用資訊服務等級協議 (SLA) 參考項目

https://sdwh.dev/posts/2023/09/Outsourcing-Service-Level-Agreement/

數位發展部指引的整理版，列出六大類：系統與服務可用性、服務指標（MTBF／MTTR／
回應時間）、永續營運（RTO／RPO／MTPD）、資安品質、服務品質、使用者體驗。
寫政府案時用來確認有沒有漏掉整類。

## 5. 政府案才需要的那一段

如果對象是公家機關，另外要寫資通安全事件通報：發現後 1 小時內通報、
等級評估時效、1–2 級 72 小時內完成處理、3–4 級 36 小時內。
民間客戶不必寫這一段（寫了反而像把法規義務攬到自己身上）。

法源：《資通安全事件通報應變及演練辦法》
