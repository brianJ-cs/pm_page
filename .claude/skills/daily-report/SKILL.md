# 每日進度報告

## 先撈證據，再寫

**不要憑印象寫。** 這個專案常常整天不 commit，所以「今天做了什麼」多半**不在 git log 裡**，
而在工作區的 diff 和 `out/` 的截圖時間上。四個地方一起看：

```bash
git log --date=format:'%Y-%m-%d %H:%M' --pretty='%h %ad %s' -12   # 今天有沒有 commit
git status --short                                                 # 沒 commit 的都在這
git diff --stat                                                    # 今天動了多少
ls -l --time-style='+%m-%d %H:%M' *.html | sort -k6,7 | tail       # 哪幾支檔案是今天存的
ls -l --time-style='+%m-%d %H:%M' out/ | sort -k6,7 | tail -20     # 驗到哪、幾點驗的
```

`out/` 那一排截圖是**最好用的一份時間軸**：檔名寫著在驗什麼，時間寫著幾點驗到那一步。
名字帶 `check2`、`check3`、`save_check` 的那種連號，就是那天卡住的地方。

看完之後再讀 `git diff` 本人 —— 完成度要講得出「動了哪個函式、為什麼」，
而不是「改了一些程式碼」。

## 格式（照抄，不要自己改結構）

```
每日進度報告
├── 今日做了什麽
│   ├── 1.xxx
│   │   ├── 細節1
│   │   ├── 細節2
│   │   └── 完成度
│   └── 2.xxx
│       ├── 細節1
│       └── 完成度
├── 今日遇到難題
│   ├── 1.yyy
│   │   ├── 問題核心
│   │   └── 怎麽解決
│   └── 一直重複問又好像修不好的
│       └── 細節
└── 進行中
    └── xxx
```

## ⚠️ 最重要的一條：框架裡面寫人話

**框架內不要出現專有名詞或函式的名字，要寫人看得懂的話。**

日報是給**人**看的 —— 多半是給不看程式碼的人看，也可能是給三個月後的自己看。
一行 `syncStickerTool()` 對讀的人來說是零資訊：他不知道那是什麼，也查不到。
**函式名、變數名、id、檔名、技術詞（postMessage、localStorage、iframe、base64…）
一律換成那件事在畫面上、在使用者眼裡是什麼。**

| 不要寫 | 要寫 |
|---|---|
| `#stickerLibBtn` 走 `openApp()` 開浮層 | 按下去在畫面中間開一張浮層，裡面就是整個貼紙編輯器 |
| `syncListButtons()` 裡跟 `logoBtn` 同一條 | 只有設計看得到這顆鈕，PM 和行銷那裡不會出現 |
| 點一格 `postMessage({addSticker})` 給畫布 | 點一張貼紙拿在手上，再點版上一格就貼上去 |
| 存進 `plan.layout` → `localStorage` | 跟著這個檔期一起存進這台電腦的存檔 |
| `boardState()` 的 `blocks` 帶著 base64 | 整張圖原封不動塞進檔期資料裡跟著存 |

**唯一的例外**：畫面上真的寫著那幾個字的東西 —— 分頁名（總體／落版／拼板）、
按鈕上的字（貼圖、匯出乾淨版）、使用者自己在講的詞（版位、格、刊頭）。
那些是這個專案的共同語言，不是專有名詞。

寫完檢查一遍：**每一行都要是「不碰程式碼的人讀了會懂」的話。**

**抽象的那幾條要生動地解釋。** 換掉專有名詞只是第一步 —— 有些事本身就是抽象的
（一種模式、一份存檔住在哪、一個東西跟著什麼一起被複製），換成白話還是空的。
這種給它一個看得到、摸得到的畫面：

| 還是很空 | 生動 |
|---|---|
| 多一種嵌在主程式裡的模式 | 同一支程式兩種穿法：自己開＝整間工作室；被請進來＝只把貼紙櫃推到前面，工作檯收進門後 |
| 只存在這台電腦的瀏覽器裡 | 像貼在自己桌上的便條，不是放進公司的櫃子 —— 換一台電腦坐下來，櫃子是空的 |
| 整張圖跟著檔期一起存 | 等於每次存檔都把整張圖影印一份夾進這本 DM，連過去三百份備份裡也各夾一份 |
| 每次打開都重讀一次 | 盤子不記上次看到的東西，是每次拉開抽屜當場數一遍 |

一條只給一個畫面，別堆比喻 —— 比喻是用來讓人看見那件事，不是用來裝飾。

## 每一段要寫什麼

**今日做了什麼** —— 一件事一個編號。細節寫「動了哪個檔案、哪個函式、為什麼這樣做」，
不寫「修改了程式碼」。**完成度要有根據**：跑過哪一行指令、看到哪一張截圖、量到什麼值。
沒驗過的就寫「沒驗過」—— 那比寫「完成」有用得多。

**今日遇到難題** —— `問題核心` 寫真正卡住的那一句（不是現象）；`怎麼解決` 寫實際做了什麼，
沒解決就寫沒解決。

**一直重複問又好像修不好的** —— 這一格是給「今天又問了一次的事」。要寫**為什麼會再問一次**：
在這個專案最常見的原因是**沒 commit** —— 東西其實跑得起來，但隔一個 session 就看不出來做過，
於是同一件事被重做／重問。今天真的沒有就寫「今天沒有」，不要湊一條。

**進行中** —— 每一條都要能接著做：下一步是什麼、卡在哪。順手把「還沒驗過的」列成一條。

## 規矩

- **框架裡寫人話**（見上面那一段，這是最重要的一條）。
- **精簡。** 一件事最多兩行細節＋一行完成度，一行講完一件事。
  日報是掃過去的東西，不是說明書 —— 理由、來龍去脈留給問起來的時候再講。
- **不編。** 查得到的才寫。使用者說過的話可以引用，推測要標成推測。
- 完成度**不寫百分比**，寫看得懂的話：「可用，未進版控」「能貼但沒驗存檔」「只驗過 console 乾淨」。
- 日報是**講給人看的**，直接輸出在對話裡就好 —— 不要順手存成檔案、不要順手 commit
（使用者要才做，見 `edit-fast` 那條「不要在中途生附加產物」）。
